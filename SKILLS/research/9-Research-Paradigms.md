# AI-PhD SKILL 之 Research Paradigms

[← 返回目录 / Index](../../README.md) · 中文原文 · [English](9-Research-Paradigms-EN.md)

读论文时，我们经常看到一条很顺的逻辑：现有方法有某个 limitation，作者发现了原因，于是提出一个 method，实验也验证了它。读多了，很容易以为科研就应该这样发生。

但实际做起来，很多工作并没有这么顺。有时是先发现问题，再想办法；有时是先试出一个有效的方法，才慢慢理解它为什么有效；还有时，最有价值的结果是发现原来的问题问得不太对。今天想聊聊几种常见的 research paradigm，以及沿着不同路径做出来的工作，各自需要把什么讲清楚。

这里的 paradigm 用得比较宽泛，指研究从哪里开始、怎样推进。这些路径会交叉，也会互相转化，很难据此给 novelty 排一个固定的高低。

先说 **Evolution**，从已有问题出发，逐步改进。确定一个 task，比如高效推理，调研 related work，找到现有方法共同的不足，通过实验定位原因，再提出解决方法。这是我觉得读起来最舒服的一类文章：读者能理解问题为什么存在，也能理解方法为什么长成这样。

难的是把 limitation 找准。比如，现有方法生成的 reasoning token 太多，只是一个起点。哪些 token 可以省，冗余在什么条件下出现，减少 token 是否真的降低了 latency，这些才决定后面的设计有没有依据。问题找得准，方法会自然很多，当然也还要看这个缺口有多值得解决。

更接近很多人日常状态的，是 **Searching**。有了 task 和 baseline，开始尝试各种 idea：改 architecture，加一个 loss，换一类数据。一部分失败了，一部分有提升，再沿着有效的方向继续做。刚开始未必有完整的解释，甚至只是觉得这个设计值得试试。我觉得这很正常，很多认识确实要等实验跑出来之后才会有。

这类工作很需要 story telling，但也容易把它用错地方。试出有效方法之后，需要继续分析收益来自哪里，什么情况下会失效。最好能根据这个解释，预测一个还没用来筛选 idea 的设置下会发生什么，再去验证。论文可以按更容易理解的顺序组织，但不必把整个过程写成一开始就想明白了一切。

**Combination**，则是把别处的思路带到自己的问题里。读了 domain A 的论文，觉得 method A 很有意思，想到自己熟悉的 domain B 可能也用得上，于是尝试迁移，再根据新任务做调整。这类工作有时非常巧妙，两个原本没什么联系的方向，因为共享某个问题结构而联系起来。

关键是把这种联系说清楚。原方法依赖什么假设，新领域是否满足，迁移时最困难的地方在哪里。Ablation 可以帮助确认各部分在当前设置下的作用，但为什么值得这样组合，还需要更具体的分析。好的迁移会让人觉得，原来这两个问题确实可以放在一起理解。

和它很接近的，是 **Fast Follow**，快速跟进新方法或新能力。比如 CoT、GRPO 或某种新的训练方式受到关注后，迅速考察它在自己领域里的用途。这里的区别主要在研究时机：一个新结果出现，让原本做不了或很少有人关注的事情变得值得一试。

如果只是把热门方法跑一遍，研究内容会比较有限；如果新领域暴露了原方法的重要限制，后面也可以发展成很深入的工作。早期工作有机会获得更多关注，但 citation 不能只靠抢先来推断。别人是否需要你的发现、数据或实现，也决定了这项工作能被用多久。

前面几种，主要都在讨论怎样做出一个方法。还有一些工作，值得单独拿出来讲。

比如 **Understanding**，把一个现象或机制弄清楚。为什么增加推理预算之后效果反而下降，为什么某种方法只在一类数据上有效？你围绕这些现象设计实验，区分几种可能的解释，最后给出规律和适用边界。[Scaling Laws](https://arxiv.org/abs/2001.08361) 对模型规模、数据量、计算量与 loss 关系的研究，就可以从这个角度理解。

理论研究也可以放在这里：从明确的假设出发，推导什么时候可行、什么时候存在限制，再看这些条件和实际问题有什么关系。一条可靠的规律、一个解释或一个反例，都可能改变后续研究的判断。没必要为了像一篇方法论文，硬加一个提升很小的新模块。

另一条路径是 **Simplification / Reassessment**，重新检查已有方法的必要性。一个复杂方法有效，其中哪些东西真的不能少？一个被认为落后的 baseline，在公平调参和预算对齐之后，是否仍然落后？[DPO](https://arxiv.org/abs/2305.18290) 也可以从简化训练流程的角度来看：在其建模假设下，把偏好学习写成直接优化 policy 的目标，省去了单独训练 reward model 和随后进行 RL 优化的步骤。

这类工作很考验比较是否扎实。没有复现出一个结果，还不足以说明原结论不成立；删掉模块后分数没降，也可能只是当前任务不需要它。但如果证据充分，告诉大家某个复杂设计其实不必要，或者某个结论只在很窄的条件下成立，本身就很有价值。

还有 **Problem Formulation**，重新定义值得研究和衡量的问题。有时，现有 task 和 metric 没有覆盖我们关心的能力。比如，[SWE-bench](https://arxiv.org/abs/2310.06770) 把真实 GitHub issue 和对应代码仓库组织成任务，让模型通过修改仓库来解决问题。这样的贡献包括任务设定、数据构造和评测方式，也影响了大家接下来会研究什么。

做这类工作，需要说明原来的评测漏掉了什么，以及新的分数能否反映目标能力。多收集一些样本、把题目变难，并不自动构成好的 benchmark。一个有用的新任务，应该让过去难以讨论的问题变得具体，让不同方法能够在可信的条件下比较。

最后一类，我会叫 **Building**，建立新的研究条件。可能是一套高质量数据，一个可交互、可复现的环境，也可能是一项降低计算成本的系统设计。[FlashAttention](https://arxiv.org/abs/2205.14135) 从 GPU 存储层级之间的数据读写入手，提高 exact attention 的计算效率，就是一个很具体的例子。这些工作让别人有机会做成以前做不了，或成本太高而不愿做的实验。

它的价值需要落到实际使用上：数据补足了什么，环境允许研究什么，系统在怎样的硬件和负载下节省了多少时间与内存。工作量很大和研究贡献很大是两件事。值得说明的是，这些建设是否改变了可研究的问题，或者明显降低了研究门槛。

一项工作完全可以从 Searching 开始，通过分析变成 Understanding，再找到一个很自然的 Evolution；也可以从跟进热点开始，最后发现真正缺的是一个合适的 benchmark。没必要因为起点不够漂亮，就急着否定它。也不用因为已经选了一条路径，就坚持把所有结果都写成新方法。

这也接着之前聊的 Taste。做研究时，我们一直在判断下一步值得花什么力气：继续改方法，补一个能区分解释的实验，重做评测，还是承认当前证据只支持一个更小的结论。能看见更多研究路径，至少会让这些选择更清楚一点。最后写论文时，把这项工作到底让我们多知道了什么、能多做什么讲明白，就已经很不容易了。
