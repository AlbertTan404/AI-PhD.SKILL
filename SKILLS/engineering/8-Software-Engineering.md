# AI-PhD SKILL 之 Software Engineering

[← 返回目录 / Index](../../README.md) · 中文原文 · [English](8-Software-Engineering-EN.md)

我觉得 software engineering 是每个 AI PhD student，不论刚入学还是快毕业，都应该懂一点的东西。尤其是在越来越少需要自己写代码的今天。

刚读 PhD 的时候，我经常在招生和实习要求里看到四个字：工程能力。那时候的理解很直接，有 idea 还不够，你得把它实现出来。论文里几行公式，落到训练代码里，可能就是几天的 debug。很多时候，实现确实比想到更困难。Talk is cheap, show me the code.

但到现在，我已经半年没有亲手写过一行代码了。对我自己的工作流来说，很多过去需要坐下来慢慢实现的东西，现在描述清楚需求，让 AI 去做就可以了。于是那句话也可以改一改：Talk is cheap, code is cheaper.

这反而让我更在意 software engineering。生成一段实现的成本降下来了，但理解这段实现、确认它做对了什么、把它接进已有项目，以及之后反复修改它，仍然有成本。一个项目今天能跑，和下个月换个数据集、接个新模型、交给另一位同学时依然容易改，是两件事。

所以，我现在想强调的工程能力，更多是一种判断力。你不一定要背出多少设计模式，或者熟练默写一套面向对象编程的标准答案，但你得知道什么样的代码值得留下，什么样的结构会让后面的工作越来越困难。这也接着之前那篇 Taste：面对几个都能跑的实现，你凭什么判断哪一个更适合这个项目？

比如，为什么很多项目会分成 docs、src、tests？文档记录怎么使用、为什么这样设计；实现负责具体行为；测试把关键预期变成可以检查的东西。分开之后，人和 agent 都更容易按问题找到需要的信息。但目录名字本身没有魔法，一个几小时就结束的小实验，完全可以只有一个脚本。工程上的 taste 包括知道什么时候值得拆，也包括知道什么时候继续拆只会增加负担。

我理解的好代码，有一个很朴素的判断标准：下一次需求变化时，需要理解和修改的东西有多少。换一个数据集，是否只需要调整数据读取和转换？换一个模型，是否可以保留评测逻辑？修改某个 loss，是否能单独检查它的数值和梯度？如果每次小改动都必须先读懂半个仓库，或者到五个脚本里同步修改同一段逻辑，这个项目就会越来越难维护。

这也是我觉得 AI coding 特别需要工程判断的地方。生成太容易了，一次需求可以多出一个脚本，一次修复可以再加一层 wrapper，做一个新实验也可以直接复制整个旧文件。如果每次只检查眼前能不能跑，时间久了，仓库里就可能堆满几个版本的同一套逻辑，谁在使用、该改哪份、哪些已经过期，都不再清楚。下一次 agent 接手，要先搜索、读文件、区分版本、追踪依赖，还可能改错入口。省下来的实现时间，就这样一点点变成了后续的 context、token 和排查成本。

当然，文件少也不自动意味着简单。把所有东西塞进一个几千行的脚本，同样会让局部修改需要大量上下文。真正值得关心的是：相关的逻辑是否放在一起，可以独立变化的部分是否有清楚的边界，完成一个局部任务是否只需要理解有限的信息。代码既要让人读懂，也要让之后接手的 agent 容易找到、理解和修改。

对 AI PhD 来说，这还直接影响实验是否可信。假如你为了验证一个新方法，复制了一份训练脚本，顺手调整了数据预处理和评测逻辑，最后指标涨了，你就得重新追问：到底是哪一处改动带来的？把方法、数据处理和评测之间的边界理清，把关键配置和行为记录下来，会让你更容易控制变量、做 ablation，也更容易发现自己其实改了不止一个东西。工程结构本身不能保证结论正确，但它可以降低验证结论的成本。

这套思维迁移到工作里，我觉得最重要的一点就是解耦。一个任务能不能拆开推进，取决于各部分需要什么输入、交付什么输出、依赖什么前提、怎样判断完成。如果这些边界没有说清楚，把任务分给几个人或几个 agent，最后往往还是所有人互相等待，改一个地方就要重新协调一圈。边界清楚，局部工作才有机会独立推进，出了问题也更容易定位。

所以，即使代码全由 AI 来写，我仍然觉得每个 AI PhD 都值得建立一点 software engineering 的概念。可以从自己的项目开始：下一次让 AI 加功能时，多看一眼它把改动放在哪里，为什么需要新文件，已有逻辑能不能复用，怎样确认这次修改没有破坏已有行为。再到下一次修改时，回头看这些选择到底让工作变容易了，还是变困难了。Taste 就在这种反馈里慢慢形成。

我并不觉得这些判断会永远只能由人来做。AI 也可以设计结构、review 和重构，你完全可以让它一起分析这些取舍。但既然你还在决定需求、分配资源、接受结果，理解这些取舍就会直接影响你能把项目推进到哪里。代码越来越便宜之后，我更在意的是：这次实现留下来的结构，会让下一次工作轻松多少。
