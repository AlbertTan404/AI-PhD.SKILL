# AI-PhD.SKILL: Software Engineering

[← Index](../../README.md) · [中文原文](8-Software-Engineering.md) · English

I think every AI PhD student should understand a little software engineering, whether they have just started or are about to graduate. That feels especially relevant now that we need to write less code ourselves.

When I started my PhD, I kept seeing “engineering ability” in admissions and internship requirements. My interpretation was straightforward: having an idea is not enough; you have to implement it. A few lines of equations in a paper can turn into days of debugging in training code. Implementation often is harder than coming up with the idea. Talk is cheap, show me the code.

But I have now gone six months without personally writing a line of code. In my own workflow, many things that once required sitting down and implementing them slowly can now be done by describing the requirements clearly and letting AI handle them. Perhaps the saying needs an update: talk is cheap, code is cheaper.

That makes me care more about software engineering. Generating an implementation has become cheaper, but understanding it, confirming what it does correctly, integrating it into an existing project, and changing it repeatedly still cost effort. A project that runs today may be difficult to adapt next month when you switch datasets, add a new model, or hand it to another student.

The engineering ability I want to emphasize is therefore a form of judgment. You do not have to memorize design patterns or reproduce a textbook answer about object-oriented programming. But you need to recognize which code is worth keeping and which structures will make future work harder. This connects to the earlier article on taste: when several implementations all work, how do you decide which fits the project best?

Consider why projects often have `docs`, `src`, and `tests` directories. Documentation records how to use the project and why it was designed this way. The implementation defines its behavior. Tests make important expectations checkable. Separating these helps both people and agents find the information they need. But directory names have no magic. A small experiment that takes a few hours may be perfectly fine as a single script. Engineering taste includes knowing when a split is worthwhile and when another split only adds burden.

I use a simple criterion for good code: how much will need to be understood and changed when the next requirement arrives? If you change datasets, can you limit the change to loading and transformation? If you change models, can you keep the evaluation logic? If you modify a loss, can you check its values and gradients independently? A project becomes harder to maintain when every small change requires understanding half the repository or synchronizing the same logic across five scripts.

This is where I think AI coding particularly needs engineering judgment. Generation is so easy that each request can produce another script, each fix another wrapper, and each experiment a copy of an old file. If all you check is whether today's task runs, the repository can gradually accumulate multiple versions of the same logic. It becomes unclear which version is used, which should be changed, and which is obsolete. The next agent must search, read files, distinguish versions, and trace dependencies, and it may still change the wrong entry point. The implementation time saved gradually becomes future context, token, and debugging costs.

Of course, fewer files do not automatically mean simplicity. Putting everything in one script with thousands of lines can also make local changes require a huge amount of context. What matters is whether related logic lives together, whether independently changing parts have clear boundaries, and whether a local task requires only a limited amount of understanding. Code should be understandable to people and easy for the next agent to find, understand, and change.

For an AI PhD student, this also affects whether experiments are trustworthy. Suppose you copy a training script to test a new method, and along the way also change preprocessing and evaluation. If the score improves, you have to ask which change caused it. Clear boundaries between the method, data processing, and evaluation, together with records of important configurations and behaviors, make it easier to control variables, run ablations, and notice when you changed more than one thing. Engineering structure cannot guarantee a correct conclusion, but it can reduce the cost of checking it.

When applying this thinking to collaboration, I find decoupling especially important. Whether a task can proceed in separate pieces depends on the inputs each piece needs, the outputs it delivers, its assumptions, and its completion criteria. If those boundaries are unclear, dividing work among several people or agents often leaves everyone waiting for everyone else. Every change then triggers another round of coordination. Clear boundaries create the possibility of independent progress and make problems easier to locate.

So even if AI writes all the code, I still think every AI PhD student benefits from some understanding of software engineering. Start with your own project. The next time you ask AI to add a feature, look at where it puts the change, why it needs a new file, whether existing logic can be reused, and how you will check that existing behavior still works. On the next revision, look back and ask whether those choices made the work easier or harder. Taste develops through that feedback.

I do not think these judgments will always belong exclusively to humans. AI can also design structures, review code, and refactor, and you can ask it to help analyze the tradeoffs. But while you are still deciding requirements, allocating resources, and accepting results, understanding those tradeoffs directly affects how far you can take a project. As code gets cheaper, I care more about how much easier the structure left by this implementation will make the next task.
